Project-specific learning guide

How this app could move from MySQL to MongoDB

A detailed tour of what changes in this Todo List project, why those changes are needed, and how MySQL + Sequelize concepts translate to MongoDB + Mongoose. This page describes a migration; it does not perform one.

Nothing in the application has been migrated. This is a learning document only. The existing API still uses MySQL through Sequelize. Make a backup and work on a branch before carrying out any real migration.

1. The two database layers

There are two related but different replacements. MongoDB replaces MySQL, the database server that stores the application data. Mongoose replaces Sequelize, the Node.js library the API uses to describe data and communicate with the database. Sequelize is an ORM for relational databases; Mongoose is an ODM (object-document mapper) for MongoDB. MongoDB's official Node.js driver is another option, but this guide uses Mongoose because its schemas and model API provide a familiar structured layer.

Current stackPossible replacementRole in this app
MySQLMongoDBThe database process/service storing users and tasks.
mysql2Bundled dependency used by Mongoosemysql2 is the MySQL network driver. Mongoose communicates with MongoDB and does not use mysql2.
SequelizeMongooseJavaScript APIs for models, validation, queries, and database operations.
SQL tables and rowsCollections and documentsRelational records become BSON documents in collections.

A simplified picture of the current app is Express route → controller → service → repository → Sequelize model → MySQL. The same layers can remain after migration: Express route → controller → service → repository → Mongoose model → MongoDB. The repository/model/database implementation changes; the API and much of the application behavior need not.

SQL concepts versus MongoDB concepts: MySQL stores rows in tables and commonly uses integer primary keys and foreign keys. MongoDB stores documents in collections and commonly uses ObjectIds. Mongoose can describe a reference from one document to another, but MongoDB does not enforce that reference as a relational foreign key.

2. How this project works today

The server has two Sequelize models:

  • users: an auto-increment integer id, a unique email, a password hash, and a creation timestamp.
  • tasks: an auto-increment integer id, integer user_id, title, optional description/image URL, completion flag, and timestamps.

A task belongs to a user by its user_id. The API stores the signed-in user's ID in req.session.userId. The task service/repository filters tasks by both task ID and user ID during updates/deletes, so each user operates only on their own tasks.

The frontend expects task objects to have an id property and currently types it as a number. The SQL column and JSON field names use snake_case (such as image_url), whereas the default timestamp fields in Sequelize are configured as created_at and updated_at.

These contracts are why a database swap is more than changing a connection string. The storage model, query operations, database error types, task ID format, and timestamp naming must all agree across the backend and frontend.

4. Dependencies and database connection

server/package.json and server/package-lock.json

From the server folder, use npm to remove the SQL packages and install Mongoose: 

npm uninstall sequelize mysql2
npm install mongoose

Keep dependencies such as Express, bcrypt, dotenv, and express-session. npm edits package.json and regenerates package-lock.json. Review the diff to make sure it changes only the intended dependency graph.

server/.env.example

Remove the MySQL settings (DB_HOST, DB_PORT, DB_USER, DB_PASSWORD, and DB_NAME) and add one MongoDB URI: 

NODE_ENV=development
PORT=3000
CLIENT_ORIGIN=http://localhost:5173

MONGODB_URI=mongodb://127.0.0.1:27017/task_app

SESSION_SECRET=replace_with_a_long_random_secret

That URI is for a local MongoDB server. A hosted MongoDB provider supplies a different URI. Put real credentials only in the local, ignored server/.env, encode special characters in URI credentials, and never commit secrets.

server/src/config/database.js

This file currently constructs and exports a Sequelize instance. Replace it with a function that validates configuration and opens the Mongoose connection: 

import mongoose from "mongoose";

export default async function connectDatabase() {
  const uri = process.env.MONGODB_URI;
  if (!uri) {
    throw new Error("MONGODB_URI must be added in server/.env");
  }

  await mongoose.connect(uri);
  return mongoose.connection;
}

A connection function makes startup order explicit and avoids opening a request listener before the database is ready. The returned connection can also be inspected by the health route.

server/src/server.js

Replace the Sequelize authenticate() call with the connection helper. The server should fail visibly rather than pretending to start when the database cannot be reached: 

import "dotenv/config";
import app from "./app.js";
import connectDatabase from "./config/database.js";

const port = Number(process.env.PORT || 3000);

async function startServer() {
  try {
    await connectDatabase();
    app.listen(port, () => {
      console.log(`Task App API listening at http://localhost:${port}`);
    });
  } catch (error) {
    console.error("Failed to start the Application: ", error);
    process.exit(1);
  }
}

startServer();

The current code already loads dotenv and listens only after authenticating, so this preserves the startup behavior while changing the database library.

5. Replace Sequelize models with Mongoose schemas

A Sequelize model maps fields to SQL columns and a table. A Mongoose schema describes document fields and a Mongoose model provides operations on a MongoDB collection. MongoDB automatically gives each document an _id, usually an ObjectId; do not define an auto-incrementing integer id.

server/src/models/user.model.js

This schema keeps the project's existing field names and timestamp behavior. The email is normalized to lowercase and trimmed; the existing request validator also lowercases it. 

import mongoose from "mongoose";

const userSchema = new mongoose.Schema(
  {
    email: {
      type: String,
      required: true,
      unique: true,
      lowercase: true,
      trim: true,
      maxlength: 255,
    },
    password_hash: {
      type: String,
      required: true,
    },
  },
  {
    collection: "users",
    timestamps: { createdAt: true, updatedAt: false },
  },
);

export default mongoose.model("User", userSchema);

unique: true requests a unique MongoDB index; it is not itself a Mongoose validation rule. The index must exist in the database for duplicate emails to be rejected. Confirm index creation as part of deployment and handle MongoDB's duplicate-key error.

server/src/models/task.model.js

The task's owner becomes an ObjectId reference to a user. This describes the relationship for Mongoose; it does not create an SQL foreign-key constraint. The application must keep checking ownership in queries. 

import mongoose from "mongoose";

const taskSchema = new mongoose.Schema(
  {
    user_id: {
      type: mongoose.Schema.Types.ObjectId,
      ref: "User",
      required: true,
      index: true,
    },
    title: { type: String, required: true, maxlength: 72 },
    description: { type: String, default: null },
    completed: { type: Boolean, default: false },
    image_url: { type: String, default: null },
  },
  {
    collection: "tasks",
    timestamps: true,
  },
);

export default mongoose.model("Task", taskSchema);

Mongoose timestamps are named createdAt and updatedAt by default. The current Sequelize models use underscored timestamp names. The repository sort and any migration script must use whichever naming choice the new schema configures. The example query later sorts by createdAt.

6. Rewrite repository operations

Repositories isolate database-specific details from services and controllers. SQL-style Sequelize methods such as findAll, where, update, and destroy need to become Mongoose queries. Keep the same exported functions and class methods where practical so most services do not need a rewrite.

server/src/repositories/user.repository.js

Login needs a user document containing password_hash, while normal authentication responses must not expose that hash. Keep those use cases separate: 

import mongoose from "mongoose";
import User from "../models/user.model.js";

export async function findUserByEmail(email) {
  // Login service needs password_hash for bcrypt.compare.
  return User.findOne({ email });
}

export async function findUserById(id) {
  if (!mongoose.isValidObjectId(id)) return null;

  const user = await User.findById(id).select("-password_hash");
  if (!user) return null;

  return {
    id: user._id.toString(),
    email: user.email,
    createdAt: user.createdAt,
  };
}

export async function createUser(email, password_hash) {
  const user = await User.create({ email, password_hash });
  return {
    id: user._id.toString(),
    email: user.email,
  };
}

Returning id as a string preserves the API's property name while adapting its value to MongoDB. The password hash remains available only to the login service, which already uses bcrypt.

server/src/repositories/task.repository.js

A complete class-shaped example follows. Notice that update and delete filters include both the document ID and the authenticated user's ID. That is an authorization boundary, not just a performance detail. 

import mongoose from "mongoose";
import Task from "../models/task.model.js";

function toApiTask(task) {
  if (!task) return null;

  const value = task.toObject();
  const { _id, __v, ...fields } = value;

  return {
    ...fields,
    id: _id.toString(),
    user_id: value.user_id.toString(),
  };
}

export default class TaskRepository {
  async findTasksByUserId(user_id) {
    const tasks = await Task.find({ user_id }).sort({ createdAt: -1 });
    return tasks.map(toApiTask);
  }

  async createTask(taskData) {
    const task = await Task.create(taskData);
    return toApiTask(task);
  }

  async updateTask({
    id,
    user_id,
    title,
    description = null,
    image_url = null,
    completed = null,
  }) {
    if (!mongoose.isValidObjectId(id)) return null;

    const task = await Task.findOneAndUpdate(
      { _id: id, user_id },
      { $set: { title, description, image_url, completed } },
      { new: true, runValidators: true },
    );
    return toApiTask(task);
  }

  async deleteTask(id, user_id) {
    if (!mongoose.isValidObjectId(id)) return null;

    const result = await Task.deleteOne({ _id: id, user_id });
    return result.deletedCount > 0 ? id : null;
  }
}

findOneAndUpdate returns the updated task when { new: true } is set. runValidators: true asks Mongoose to run applicable schema validators for the update. deleteOne reports a deleted count rather than returning the deleted row, so the example returns the ID when deletion succeeded, matching the existing repository's success/null pattern.

This approach returns a task object after update, while the SQL version returns an ID. The current task controller sends the repository result in its response. If preserving that exact response shape matters to external API clients, deliberately keep returning the ID, or document and test the response-shape change.

7. IDs, validation, and the API contract

MongoDB ObjectIds are commonly represented in URLs and JSON as 24-character hexadecimal strings, for example 66f1a86b4a246aef77000001. This is not a number. The frontend must stop using numeric task ID types, and backend routes should reject malformed IDs before a Mongoose query can throw a cast error.

server/src/validators/task.validator.js

Add an ObjectId schema and parameter middleware while keeping the existing task body schema: 

import { z } from "zod";

export const taskSchema = z.object({
  title: z.string().trim().min(1, "Title is required").max(72),
  description: z.string().trim().optional().nullable(),
  completed: z.boolean().default(false),
  image_url: z.string().trim().url("Must enter a URL").optional().nullable(),
});

const taskIdSchema = z.string().regex(/^[a-f\\d]{24}$/i);

export function validateTaskId(req, res, next) {
  const result = taskIdSchema.safeParse(req.params.id);
  if (!result.success) {
    return res.status(400).json({
      message: "Invalid task ID",
    });
  }
  next();
}

This middleware gives malformed IDs a clear HTTP 400 response. Another valid design is a shared route-parameter validation helper. Avoid silently treating every database error as “not found”; real connection and query failures should still reach the error handler.

server/src/routes/task.routes.js

Apply the new validator to both routes containing an ID, and leave body validation on the update route: 

import { validateTaskId } from "../validators/task.validator.js";

router.put("/:id", validateTaskId, validate(taskSchema), updateTask);
router.delete("/:id", validateTaskId, deleteTask);

Keep the existing router.use(authenticate) so these operations still require a signed-in user. The route examples show only the lines to change; retain the other imports and routes already present in the file.

API ID conversion: keep MongoDB details behind the API

MongoDB documents use _id; the existing frontend reads task.id. Convert _id to a string id in the repository, as in toApiTask above. This lets the existing routes and JSON field name stay unchanged without making the UI depend on MongoDB's internal field naming.

server/src/controllers/auth.controller.js

Replace the Sequelize import of UniqueConstraintError. MongoDB reports duplicate key/index errors with error code 11000. Keep the signup response as HTTP 409: 

// Remove: import { UniqueConstraintError } from "sequelize";

if (error && typeof error === "object" && error.code === 11000) {
  return res.status(409).json({
    message: "An account with this email already exists",
  });
}

Keep the bcrypt service and session regeneration/save logic. The repository now returns a string ID from user creation, so req.session.userId = user.id continues to work; it now stores that string ObjectId rather than an integer.

8. Other backend files to update or review

server/src/routes/health.routes.js

The route currently calls Sequelize's authenticate() and checks for three MySQL settings. Replace that with a check for MONGODB_URI and Mongoose connection readiness. Do not return the URI or credentials: 

import { Router } from "express";
import mongoose from "mongoose";

const router = Router();

router.get("/", (req, res) => {
  res.json({ status: "ok", message: "Task App API is running." });
});

router.get("/db", (req, res) => {
  if (!process.env.MONGODB_URI) {
    return res.status(503).json({
      status: "error",
      message: "Set MONGODB_URI in server/.env before checking the database.",
    });
  }

  if (mongoose.connection.readyState !== 1) {
    return res.status(503).json({
      status: "error",
      message: "Could not connect to MongoDB. Check the service and MONGODB_URI.",
    });
  }

  return res.json({
    status: "ok",
    database: mongoose.connection.name,
  });
});

export default router;

The Mongoose connection state values distinguish disconnected, connecting, connected, and disconnecting states; 1 means connected. If the project wants health-check failures logged, add deliberate logging; do not hide unexpected errors behind a success response.

server/src/services/auth.services.js

This service hashes passwords with bcrypt and compares the hash on login. Those operations are independent of SQL and should remain. Verify that findUserByEmail still returns a document containing password_hash, and that the login response returns a string id plus email—not the hash.

server/src/services/task.services.js

The service coordinates user checks and repository operations; it does not directly use Sequelize. Its task and user IDs will now be strings. Preserve every user ownership check, and ensure service functions don't reject valid ObjectId strings merely because the old integer code assumed numbers.

server/src/controllers/task.controller.js

Controller calls can mostly remain because IDs arrive as strings in route params and repositories now accept strings. Review the not-found status: this project's current controller returns 401 for missing/invalid task results. A more conventional distinction is 400 for malformed ID (handled by route validation) and 404 for a valid ID that is missing or not owned by the current user. If changing status codes, treat that as an intentional API behavior change and test clients.

server/src/middleware/authenticate.js

The middleware reads req.session.userId and calls findUserById. Keep this flow. Because the session now holds an ObjectId string, the repository should safely reject a missing or malformed session ID and return no user; the middleware can then respond as unauthenticated instead of allowing a Mongoose cast error to become an HTTP 500.

server/src/app.js (optional session-store work)

Switching the user/task database does not automatically change Express session storage. This file currently uses express-session's default in-memory store. That is generally unsuitable for production or multiple API instances because sessions disappear on restart and are not shared.

If persistent sessions are needed, separately install and configure a MongoDB-compatible store such as connect-mongo in app.js. This is a separate production concern; do not confuse it with replacing Sequelize models. Keep the session secret, cookie protections, and current session behavior in place while making that decision.

If the API translates MongoDB _id into string id, the existing endpoint URLs and JSON property names can stay. TypeScript must reflect the new ID type so comparisons and callback signatures stay correct.

Also update addTask, updateTask, and any callbacks that accept a task ID. Existing URL interpolation and strict equality comparisons continue to work with strings, provided the API always returns string IDs.

frontend/src/components/TaskForm.tsx

Change the ID argument in onAddTask and onUpdateTask to string. The edit URL already interpolates the ID, and the create handler should pass the response's string result.task.id to the parent.

Change the onDelete and onToggleComplete callback parameter types to string. React keys and HTML IDs accept strings, so key={task.id} and taskStatus-${task.id} need no structural rewrite.

10. Existing MySQL data requires a separate migration

Replacing the connection does not copy the MySQL records into MongoDB. If there is data to keep, plan and verify a separate export/import before pointing users at the new database.

  1. Take and verify a restorable MySQL backup. Record counts of users and tasks.
  2. Export the user and task rows and preserve a mapping from each old integer user ID to the new MongoDB ObjectId.
  3. Insert users first. Preserve password_hash exactly so existing passwords still work; do not hash the hash again.
  4. Insert tasks after rewriting each task's user_id using the saved old-ID-to-new-ID mapping.
  5. Preserve timestamps, nullable values, completion booleans, and image URLs deliberately; check how the export format represents them.
  6. Compare record counts, sample documents, email uniqueness, and task ownership. Run application tests against the imported database.
  7. Choose a cutover/rollback window. Keep the old database and verified backup until MongoDB is proven correct.
Do not copy integer IDs into the ObjectId field. MongoDB's ObjectId and the old SQL integer key are different ID systems. The task-owner mapping is essential; without it, tasks can become orphaned or attached to the wrong user.

Existing login sessions may need to be invalidated or users may need to sign in again. A session that still contains an old numeric user ID cannot identify the new MongoDB user unless a deliberate mapping and compatibility plan is implemented.

11. Security and operational considerations

  • Neither stack is automatically more secure. Security depends on correct configuration, validation, authorization, secrets management, updates, and database access controls.
  • Validate input. Validate request bodies and ObjectId route parameters. Never pass arbitrary client-provided query operators or filters directly into MongoDB.
  • Keep authorization in database filters. Task update/delete filters should contain both _id and the signed-in user_id.
  • Keep secrets private. Store production URIs/passwords outside source control. Restrict MongoDB network access and database user privileges.
  • Protect account data. Never return password_hash. Continue bcrypt hashing and use TLS for hosted database connections as required by the provider.
  • Plan indexes. Ensure unique email and task-owner indexes exist. A schema option alone should not be treated as proof that a production index was created.
  • Observe failures. Database connection and unexpected query failures should be logged/reported; do not turn them into success-shaped responses.
  • Back up and test restore. Backups are only useful if restoration has been tested.

MongoDB's flexible documents can be convenient, but relational constraints, joins, and transactions may require different design decisions. This app's user-to-task relationship is small and can be modeled in MongoDB, but the migration is not automatically simpler or safer than staying with MySQL.

12. Suggested implementation order and verification

  1. Work on a branch; inventory current data and make a restorable MySQL backup.
  2. Install Mongoose, set a local MONGODB_URI, and confirm startup fails clearly if the database is unavailable.
  3. Implement schemas and repositories. Test unique email handling, public user fields, timestamps, sort order, and owner-scoped task operations.
  4. Implement ObjectId route validation and string IDs. Check API responses still use id and never expose _id unless intended.
  5. Update the frontend types, run its build/type-check, and verify task creation/edit/delete/toggle through the UI.
  6. Test signup, login, logout, current-user endpoint, database health endpoint, malformed IDs, unknown IDs, and cross-user task access.
  7. If importing existing data, compare counts and ownership and test using migrated accounts before cutover.
  8. Update DEPENDENCIES.md, deployment environment variables, and operational/backup documentation; remove obsolete MySQL settings from active deployment configuration.
